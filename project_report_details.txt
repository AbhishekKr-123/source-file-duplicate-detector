1.1 Identification of client & need:
- Client: students, teachers/evaluators, and small development teams who
  collect many C source files (lab submissions, assignment folders, backups).
- Need: manually opening each pair of files to find copies is slow and

1.2 Relevant contemporary issues:
- Academic integrity: plagiarism detection in programming assignments.
- Source code management hygiene: redundant copies, dead code, backup sprawl.
- Code reuse auditing in small teams without heavy external tools.
- Educational value: demonstrates real text-processing pipelines in pure C.

1.3 Problem identification:
- A character-by-character comparison declares these two identical programs
  DIFFERENT because formatting and variable names differ:
    File 1:                          File 2:
    int main()                       int main(){
    {                                int x=10;
        int a = 10;                  int y=20;
        int b = 20;                  printf("%d",x+y);
        printf("%d", a + b);         return 0;
        return 0;                    }
    }

pairwise similarity using LCS; 9. classify similarity into bands; 10. show a

SECTION 4 — CHAPTER 2 CONTENT (Literature Survey)
--------------------------------------------------------------------------------
2.1 Timeline of the problem worldwide (background facts for ChatGPT to expand):
- 1970s-80s: Unix utilities diff/cmp established longest-common-subsequence
  based file differencing (Hunt–McIlroy diff algorithm, 1976).
- 1978: Wagner–Fischer dynamic programming formulates LCS with O(m*n) time,
  O(min(m,n)) space possible with two-row optimization (this project uses the
  two-row variant).
- 1990s: MOSS (Measure of Software Similarity, Stanford, Schleimer et al.
  2003) popularized tokenization-based plagiarism detection; the winnowing
  algorithm selects fingerprints from k-grams.
- 1998+: Plague, JPlag (token-based), and GPLAG (graph/AST based, 2006) marks
  the progression token -> structure.
- Simian, PMD CPD: token-stream duplicate detection in industry linters.
- djb2 hash (Daniel J. Bernstein) used here as a simple string/file hash.

2.2 Proposed solutions by different approaches (for a comparison table):
- Diff tools (diff, cmp): line/byte differencing; sensitive to reformatting.
- Hash-based dedup (md5/sha over file): catches only byte-identical files.
- Metric/map-based (Halstead, token n-grams): statistical similarity.
- Token-based (MOSS, JPlag, this project): robust to formatting and renaming.
- AST-based (GPLAG, Clone Detective): structure-aware, heavier to implement.

2.3 Summary linking literature with this project:
This project reimplements the classic detection pipeline (bytes -> hash ->
normalized text -> tokens -> LCS) as a small, self-contained academic tool in
pure C, choosing LCS over n-gram fingerprinting for explainability, and adding
an identifier-normalization mode for rename-resistant comparison.

2.4 Problem definition: Given a set of N C source files, automatically
identify every pair that is byte-identical and rank every remaining pair by
structural similarity that survives formatting changes, comment insertion,
and identifier renaming.

2.5 Goals and objectives (13 objectives):
1. Read C source files from the user's system.
2. Store and manage multiple source files (add/remove/list/search/validate).
3. Calculate file size, line count, and character count.
4. Detect exact duplicate files (with size-first O(1) rejection).
5. Ignore irrelevant formatting differences (whitespace removal).
6. Remove comments safely (state machine protecting strings/chars).
7. Tokenize source code into meaningful elements (8 token types).
8. Calculate similarity using LCS dynamic programming.
9. Compare all N(N-1)/2 unique file pairs automatically.
10. Display an N x N similarity matrix.
11. Classify similarity into defined percentage bands.
12. Generate a persistent duplicate-analysis report (duplicate_report.txt).
13. Demonstrate efficient C file handling, dynamic memory, and modular design.

SECTION 5 — CHAPTER 3 CONTENT (Design Flow / Process)
--------------------------------------------------------------------------------
3.1 Concept generation (candidate ideas considered):
- (a) Pure byte-level differencing utility — rejected: fails on reformatting.
- (b) Line-hash fuzzy diff — better but still fails on comments/renames.
- (c) Full compiler/AST comparison — strongest but far beyond C-course scope
  (requires parser generator, symbol tables).
- (d) SELECTED: multi-level pipeline = exact bytes -> normalized text ->
  tokenization -> LCS similarity, with identifier normalization toggle and
  hashing as an optimization. Explainable, pure C, no external dependencies.

3.2 Evaluation & selection of specifications/features:
Feature matrix (ChatGPT: put in "Table: Feature comparison of alternatives"):
  Criterion                    (a)bytes (b)line-hash (c)AST (d)multi-level
  Detects reformatting            No        Yes         Yes      Yes
  Detects comment insertion       No        Yes         Yes      Yes
  Detects identifier renaming     No        No          Yes      Yes(partial)
  Memory/CPU cost                 Tiny      Small       Heavy    Moderate
  Implementable in pure C         Yes       Yes         No       Yes
  Explainable to examiners        Yes       Yes         Complex  Yes

3.3 Design constraints & issues considered:
- Regulations/ethics: tool reports similarity only; it does NOT conclusively
  prove plagiarism (two students may independently write similar code). The
  report text states this limitation.
- Economic: zero-cost — free GCC toolchain, no licenses, no cloud.
- Environmental/safety/social: offline desktop tool, no data leaves the
  machine, no network code at all.
- Health/ergonomics: simple numbered menu, predictable input flow.
- Manufacturability/sustainability: single build command, portable ANSI C,
  compiles unchanged with gcc 6.3 on Windows/MinGW and Linux.
- Political/professional: respects examiners — every similarity value prints
  the classification label directly beside it.

3.4 Analysis subject to constraints: O(N^2) pairwise comparisons and
O(A*B) LCS are acceptable for classroom file counts (N <= 100, files < a few
hundred KB). Hash pre-filter prevents O(L) byte scans for most pairs. LCS
memory reduced from O(A*B) to O(min row) using rolling two-row DP.

3.7 Implementation plan (module-wise function list — cite in report):
- file_manager.c: struct SourceFile {int id; char filename[100];
  char filepath[300]; long fileSize; int lineCount; int charCount;};
  fixed array of 100; globals g_files, g_fileCount, g_nextId;
  functions fmt: fm_add, fm_remove, fm_display, fm_find_by_id, fm_exists,
  fm_validate_path.
- file_reader.c: fr_read_content (fseek/ftell sized malloc + fread),
  fr_file_size, fr_get_stats (counts chars/lines per byte).
- normalizer.c: norm_remove_comments — 5-state machine
  (NORMAL, IN_STRING, IN_CHAR, IN_LINE_COMMENT, IN_BLOCK_COMMENT) handling
  escapes; norm_remove_whitespace — deletes all isspace() characters;
  norm_normalize = comments then whitespace.
- tokenizer.c: struct Token {char value[100]; int type;}; token types:
  Keyword, Identifier, Number, Operator, Separator, Bracket, String, Char.
  Recognizes 21 multi-character operators (== != <= >= && || ++ -- += -=
  *= /= %= &= |= ^= <<= >>= ->), 37 C keywords, numbers with '.' suffixes,
  escaped characters inside strings/chars. tok_normalize_identifiers replaces
  every identifier with "ID" for the rename-resistant mode.
- comparator.c: cmp_exact (size check first, then byte-by-byte),
  cmp_hash_file / cmp_hash_djb2_str (djb2 hash 5381 base, used only as a
  fast reject — hash match is still verified by byte comparison because hash
  collisions are possible), cmp_normalized_equal.
- similarity.c: sim_lcs_length — LCS DP with 2 rolling arrays (each iterate
  over shorter token list as columns), O(A*B) time, O(B) memory;
  sim_score_from_lcs = LCS / max(nA,nB) * 100 (if both token lists empty ->
  100.0); sim_files = read -> strip comments -> tokenize -> (optional ID
  normalization) -> LCS -> score; sim_classify thresholds:
      100%            Exact Duplicate
      90-<100%        Highly Similar
      70-<90%         Similar
      50-<70%         Moderately Similar
      <50%            Low Similarity
- report.c: rep_build_matrix (fills N x N, reuses symmetry j<i = mat[j][i]),
  rep_print_matrix, rep_find_exact (hash pre-filter + verify),
  rep_find_similar(threshold), rep_generate (writes duplicate_report.txt with
  date via time.h ctime), rep_complete_analysis.
- main.c: menu loop (fgets-based robust input), quote stripping, two-file
  comparison view, threshold prompt, dispatch to modules.

4.6 Complexity analysis (state in results chapter):
- Reading a file: O(L) per file.
- Exact pair check: O(1) size compare + O(L) worst case; hash pre-filter
  makes typical cost O(1) with rare O(L) verification.
- Pairwise comparisons: N(N-1)/2 pairs -> O(N^2) pairs; O(N^2 * L) naive text
  work; with LCS O(A*B) per pair => O(N^2 * T^2) total token work where T =
  average tokens per file.
- Matrix storage: O(N^2).
- LCS implementation detail: two-row rolling DP -> O(min(A,B)) extra memory.

SECTION 7 — CHAPTER 5 CONTENT (Conclusion, Future Scope)
--------------------------------------------------------------------------------
Conclusion points:
- Delivered a working multi-level duplicate/similarity detector in ~700 lines
  of portable, standard C with zero external dependencies.
- Demonstrated the full pipeline: file I/O, statistics, hashing, state-machine
  preprocessing, lexical tokenization, dynamic programming (LCS), matrix
  computation, classification, persistent reporting.
- Real-run results show perfect clustering of the same program under
  reformatting + comments, correct isolation of an unrelated program, and
  correct handling of empty files and string-embedded comment syntax.

Limitations (state honestly, from format requirement "deviation from expected
results"):
- Cannot prove plagiarism; finds similarity, a human must review.
- Not semantic: two differently-written programs solving the same task may
  score low despite identical functionality.
- LCS is O(T^2) per pair: very large files slow the matrix down.
- Identifier normalization can inflate similarity of unrelated programs that
  share simple skeletons (observed: 52.5% for factorial vs sum program).
- Only .c/.h style text; string-heavy files shift scores (Tokenizer keeps
  string literals intact — by design).

Future enhancements:
- GUI front-end (Win32/GTK).
- Directory & recursive directory scanning instead of manual add.
- HTML report with colour-coded matrix; CSV export.
- AST-based structural comparison (parser for C subset).
- Multi-language tokenizers (C++, Java, Python).
- Parallel pair processing (threads) for large N.
- Winnowing/k-gram fingerprinting for very large repositories.

ABSTRACT draft (expand to one page, double-spaced, Times New Roman 14):
"The Source File Duplicate Detector is a console-based application written in
standard C that automatically detects exact duplicates and measures similarity
between C source files. Manually comparing collections of student submissions
or backup copies is slow, and byte-level comparison fails when files differ
only in formatting, comments, or variable names. The system reads and stores
source files with size, line, and character statistics; detects byte-identical
files first (with an O(1) size check and a djb2 hash pre-filter); then
performs normalized comparison by removing comments with a five-state
parser that protects string and character literals, and eliminating all
whitespace. Source code is tokenized into keywords, identifiers, numbers,
operators, separators, brackets, strings, and character constants, and an
optional mode replaces identifiers with a generic symbol so renamed-variable
copies are still recognized. Pairwise similarity between files is computed as
the Longest Common Subsequence of token lists, normalized by the longer file,
scored as a percentage, and classified into five bands from Exact Duplicate to
Low Similarity. All N(N-1)/2 pair results are assembled into a symmetric
similarity matrix and written to a persistent report file, duplicate_report.txt.
The tool requires no internet, database, external library, or GUI, compiles
cleanly with GCC, and was validated on eight crafted test files: byte copies
scored 100%, reformatted and commented copies clustered at 100% after
normalization, an unrelated factorial program scored under 70%, and a file
containing comment-like strings was processed correctly. The project
demonstrates C file handling, structures, pointers, dynamic memory, state
machines, lexical analysis, and dynamic programming in one coherent pipeline."
